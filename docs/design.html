QualGentBench — the hunt benchmark, by design

design doc · 2026-08-04, updated 2026-08-20 · owner: Tameem · status: living document

Take real open-source Android apps, deliberately write known defects into their source, build them, and hand the resulting APK to a coding agent framed exactly as a QA engineer would receive it: here is a build, here is what the product team says each area should do, go verify it.

The agent gets a device and a step budget. It never sees the source, is never told that anything is wrong, and is never told how many defects exist. Because we wrote the defects, the answer key is exact — and every claim the agent makes is replayed on the device to check it is demonstrable. No human judgement and no LLM grader anywhere in the loop.

This is the narrative design doc. The concise references live beside it: architecture.md (how an episode, the meters and replay verification fit together) and scoring.md (every formula and constant).

Hunt mode is the headline format: one episode per app, the whole app under test at once, the agent decides what to test and how deep to go. That is the thing a QA engineer is actually paid for, and it is the only format that can measure it.

Guided mode still exists and is not the board. Guided means one feature per episode, with the feature named for the agent. It is the authoring and debugging harness — it is how every dead bug in this project was found, because attribution is unambiguous. New apps are onboarded in guided mode and then join the hunt board. Never merge the two tables.

01Build time versus run time

This is the single most misread part of the design, so it comes first. The APKs are compiled once, offline, weeks before any benchmark run. Nothing is built during an episode.

The mechanism that makes this work: buggy.apk contains every seeded defect, each one wrapped in a runtime flag check. A text file written to the app's private storage at install time decides which of them are actually live.

Flags file at /data/data/<pkg>/files/qgb_flags.txtBehaviour
missingevery defect live — legacy fallback, so a forgotten write can't silently clean the app
presentonly the listed ids are live
emptygenuinely clean app — a zero-defect episode

Hunt writes the app's full seeded set today. The same mechanism is what makes random active subsets and 15–20% zero-defect episodes possible without rebuilding: 2 APKs per app (~56 total, ~1.7 GB) instead of 2ⁿ variants (~900 APKs, ~28 GB).

02The corpus

Target: 6 easy · 10 medium · 12 hard = 28 apps. Defects scale with tier, which also lands the tier mix on the intended 10 / 30 / 35 / 25 L1–L4 distribution without forcing it.

TierAppsCharacterDefects/app
Easy6single purpose, immediate symptoms3
Medium10multi-screen, persisted state4
Hard12transactions, recurrence, media libraries, vaults5

Seeded and device-verified today: 16 apps · 64 defects · 71 controls, both tiers hunt-ready and gate-green. The APKs are drawn from projects like fossify-calendar, fossify-gallery, fossify-messages, uhabits, simpletimetracker, opencalc, moneymanagerex, aegis and keepassdx.

Selection rules that actually gate an app

  • compileSdk ≤ 36, non-KMP, non-Flutter, one obvious application module, debug-buildable. Without run-as there is no ground truth.
  • Readable local persistence. pf-food-tracker passed everything else and then failed both its controls with file is not a database — SQLCipher. Screen for it before authoring.
  • No permission or SAF wall on launch. fossify-voicerecorder costs six interactions of pure environment setup every episode and is not pre-grantable over adb.
  • Verdicts must not depend on timing or image content. That killed fossify-camera and pf-interval-timer.
  • Domain diversity. Don't ship five note apps.

03Authoring one app

Seven stages, run offline, once per app. Two of them are gates that can send the work back.

Write the defects as source patches. Each is a single-site, mutation-style edit — flip an operator, skip a save, invert a boolean — wrapped in the runtime flag gate:

fun delete(event: Event) = viewModelScope.launch(Dispatchers.IO) {
    if (!QgbFlags.on("delete-broken")) eventDao.deleteEvent(event)
}

Deleting a birthday now removes it from the screen but never from the database, so it comes back when the list is re-read. The UI lies; only persistence tells the truth. Trace click handler → view model → service → DAO before patching. Three dead bugs so far were all the same mistake: patching a plausible implementation the UI never calls.

The verdict flip is the gate that has paid for itself twice. Same build, flag file empty versus only that one id set, must behave differently, reproduced by hand. It caught a uhabits patch that compiled and injected cleanly but was never reached, and a simpletimetracker proof that was invalid because a confirmation dialog wasn't being tapped. A defect is not seeded until its flip has been observed.

The hunt spec is what makes the app scoreable: areas (every scored surface, each broken with a bug_id or an ok working control), probes (per-area keywords that must appear in the agent's device interactions), brief (acceptance criteria in product language, written identically for defects and controls), step budget (derived from measured cost), and optional device_setup.

04What the agent is handed

One episode per app. It receives the app installed and launched on a fresh pm clear, runtime permissions pre-granted, animations disabled, a brief, and a step budget. It does not receive the source, the defect count, any statement that defects exist, or any hint about how a defect would show itself.

You are a QA engineer. This build of a birthday-reminder app has been handed
to you for release sign-off. The list below is what the product team says each
area should do. Verify them on the device and report what you actually observe.

SPECIFICATION
  - add_event: a birthday you add is listed afterwards.
  - favorite: a birthday you mark as favourite stays marked.
  - edit_event: a birthday's details after editing are the details you entered.
  - delete_event: a birthday you delete is no longer listed.
  - event_list: the list shows the birthdays that exist.
  - settings: settings screens open and the chosen options are what stays selected.

Three properties of the brief are load-bearing:

  • Neutral. It never says "bug", "broken", or "find the defects", and never suggests a detection technique. An earlier birday brief said problems only reveal themselves after you close and reopen the app — that hands over the entire difficulty of the L3 persistence defects. check_tier_ready.py greps for this class of leak and fails the tier.
  • Defects and controls are written identically. Nothing in the wording distinguishes them.
  • Ground truth ⊋ brief. The answer key is the whole area list, so a find outside the named areas is still scoreable, and a false report on an unlisted-but-working area still costs.

The report contract

The agent reports each area as it finishes examining it, not batched at the end. The primary channel is a findings.yaml file carrying, per area, the verdict and a replayable reproduction (steps anchored on visible text, plus a checkable expectation) — that reproduction is what verification later re-executes. A plain report line remains as a fallback channel:

AREA: <area> | VERDICT: as_specified|deviates|blocked | EXPECTED: <spec> | ACTUAL: <observed>
  • as_specified / deviates, not ok/broken — ok/broken pre-frames the answer.
  • blocked is a real, first-class verdict for an area it genuinely could not exercise. It earns nothing and costs nothing: blocked beats guessing (no false-report cost) and loses to testing (no recall credit). Abuse is self-limiting — blocked areas don't count toward coverage, so blocking everything reads unmistakably as "did not test this app".
  • Incremental reporting buys three things: a truncated episode keeps what it already banked, we learn the call index of every finding, and the evidence check becomes temporal — the device work justifying a verdict must come before the verdict.

05One episode, start to finish

isolate_app_under_test exists because the other benchmark apps accumulate on the device, and a single back-press once dropped an agent into a different seeded app; that episode recorded 100% coverage and looked clean.

One step the diagram predates: between staging and the agent, the harness now takes a cold snapshot of the app's data — launch once (first-run work happens), settle, force-stop, tar, launch again for the agent. Replay restores that tar and cold-launches the same way, so agent-start and replay-start are the same screen by construction.

How a step is charged

  • A step is one interaction — one tap, one swipe, one text entry, one screen read — whatever transport carried it. Typing a 30-character name is one type; reading the screen is one observe however many calls it took.
  • Counting happens at two harness-owned proxies below the agent: a meter on the adb socket (bare arm) and a meter in front of the MCP server. The agent cannot see them, and a script run by path is counted the same as typed commands — chaining buys nothing.
  • Enforcement is a pre-tool hook that reads the meters' shared file and fails closed: an unreadable meter stops the episode rather than letting it run unmeasured.

Every result is stamped with budget_accounting: interaction-v3, and derive_budgets.py refuses to measure across accounting versions, so a rule change becomes "go recalibrate" rather than a confidently wrong number.

Two arms are run per app, switched by one flag: --mcp-server present (the agent gets device tools) or absent (a bare agent driving raw adb). The uplift is the diff between them. After the episode, staging's cold app-data snapshot is what makes every claim replayable: verification restores it and re-executes the agent's own reproductions with the defects on and off.

06Scoring

The evidence gate

A deviates verdict on a seeded defect is credited only if both hold:

  • Probe — a keyword specific to that area appeared in the agent's own device interactions (tool arguments, screen observations, or raw adb output) before the verdict was banked.
  • Work — at least 3 device operations had occurred before the claim.

This exists because without it the benchmark measures priors, not testing. A blind heuristic — "anything named delete/edit/sort is broken, anything named view/list is fine", zero device interaction — used to score a mean of 0.911 and beat the real agent. Claims that fail the gate are surfaced separately as unverified_broken, counted as missed, and are auditable per episode.

The formulas

recall     = Σ W(tier) over defects found / Σ W(tier) over all defects   # TIER-WEIGHTED
precision  = TP / (TP + FP)                                              # count-based
F1         = 2·P·R / (P + R)
FP%        = total false reports / total working areas, summed across the run

earliness  = clamp(1 − steps_used / budget, 0, 1)
speed      = 1 − 0.035 × (1 − earliness)  # only when the agent has probe-verified finds

overall_raw = recall × speed − 0.25 × FP            # signed — used for RANKING
overall     = max(0, overall_raw)                   # clamped — the reported score
  • Recall is tier-weighted so finding the subtle L3 persistence defect is worth six times finding an obvious L1. Unweighted recall scores "found the two easy ones, missed the hard one" identically to the reverse.
  • Precision is count-based, not weighted: a false report costs a human triage cycle regardless of which area it was about.
  • F1 is reported for continuity with standard IR practice. It is not the headline.
  • Precision appears exactly once in the headline — as the cost term. An earlier form multiplied by precision as well, counting it three times; it compounded hard enough that an agent which found all three seeded defects scored −0.33.
  • Speed is a tie-breaker, not a lever. It is written as a discount for slowness rather than a bonus for haste, so a perfect episode tops out at exactly 1.0 and needs no cap. The earlier min(1, recall × (1 + B × earliness)) form capped the bonus away for every agent at recall 1.0 — the exact agents a board has to separate. Two real birday runs, 68 steps and 89 steps, both scored 1.0000.
  • W = 0.035 is derived, not chosen. It must sit below the smallest tier-weighted quality gap in the corpus, which is fossify-notes at 0.0385 — its weights are 10/6/1/6/3, so missing the L1 costs only 1/26 of recall. A test derives that bound from the live corpus and fails if a re-tiering makes the weight unsafe. Read tiers through exploration_task: they are merged in from the task list and are absent from the raw exploration.features YAML, which reads as untiered and gives a bound five times too loose.
  • The score can go negative and ranks negative. Display is clamped to [0, 1] so the reported number is a percentage; ranking uses overall_raw, because clamping alone would make spraying tie with doing nothing.

Worked example — birday

3 seeded defects at L3 / L3 / L2 (weights 6, 6, 3 = 15), 5 working controls, budget 500. The agent finds the two L3s, misses the L2, files no false reports, uses 150 steps:

recall      = (6 + 6) / 15                     = 0.800
precision   = 2 / (2 + 0)                      = 1.000
F1          = 2 × 1.0 × 0.8 / 1.8              = 0.889
earliness   = 1 − 150/500                      = 0.700
speed       = 1 − 0.035 × (1 − 0.700)          = 0.990
overall     = 0.800 × 0.990 − 0                = 0.792

Same episode, but with 2 false reports added:

precision   = 2 / (2 + 2)                      = 0.500
F1          = 2 × 0.5 × 0.8 / 1.3              = 0.615
overall     = 0.792 − 0.25 × 2                 = 0.292

Recall is untouched — it found the same defects. The entire cost of the two false reports lands in overall, which is the intended behaviour.

Try it — what actually moves the score

Two agents on birday: 3 seeded defects weighted 6 / 6 / 3, 5 working controls, a 500-step budget. Drag anything. The scenario buttons animate both agents into a named situation.

Three things the sliders make obvious, and they are the whole design:

  • Defects found dominates everything. On birday one L3 is worth 0.40 of the score. No amount of speed reaches it — the entire speed term is 3.5%.
  • A false report costs 0.25 — about the same as missing the L2 defect. It is the only term that can push the score below zero, which is what keeps spraying unprofitable.
  • Speed only decides ties. Set both agents to 3/3 with no false reports and the bars separate purely on steps; give one agent a missed defect and no step count can rescue it.

07Anti-gaming

Four defenses, each of which exists because the thing it defends against actually happened:

  • Working controls are the majority of areas. Easy tier is 54 areas: 24 defects, 26 controls (the rest collateral) — a 44% deviation rate. At 68% an agent could score F1 0.81 by reporting "everything is broken" without touching the device. check_tier_ready.py fails a tier above 55%.
  • The evidence gate — verdicts must be earned on-device, temporally before the claim.
  • Tier weights — so recall can't be farmed on the cheap defects.
  • The flag gate enables random active subsets and zero-defect episodes, so an agent can never assume that every run contains a defect.

scripts/adversary_check.py scores four synthetic agents through the real scorer and asserts the honest one wins. Live numbers, easy tier, today:

AdversaryScore
A1 spray — every area deviates, ~no device work−1.02
A2 crud-prior — "mutations deviate, read-only areas are fine", correctly paced−0.30
A3 oracle-guess — knows the answer key, correctly paced, no feature-specific device work0.000
H honest — same correct verdicts, each feature exercised before its claim1.000

A3 is the one that matters: it is the strongest possible guesser. It scores zero.

08Episode validity

A score is meaningless if the episode wasn't a real attempt. Three conditions are recorded per episode and any of them invalidates it:

  • truncated — hit the step budget. Only invalid if coverage is incomplete; an episode that banked every area and was killed one call over budget has complete data.
  • dead — the agent's loop died almost immediately (<5 device operations). One model wrote a plan instead of calling a tool, its CLI ended the turn, and it scored 0.0 having done nothing. That is a CLI-compatibility failure, not a QA result, and must not be readable as one.
  • off_app — the agent left the app under test and tested a different one. The finishing package is recorded on every episode regardless.

scripts/check_tier_ready.py is the gate before quoting any number. It checks brief neutrality, deviation rate, budgets present, every defect tiered, the adversary check, budgets versus what the hook actually charged, and the last run's truncated/dead/off-app counts. Easy tier today: READY.

The uplift measurement is a diff, not a metric the benchmark encodes. Run the same agent twice and subtract. The benchmark neither knows nor cares what is driving the phone. Corollary the team should internalise: the bare arm has to be visibly generous, because "your baseline was crippled" is the first thing a competitor will say.

11Honest limits

Say these before someone else does.

  • Seeded ≠ real. Mutation-style seeds correlate with real faults (Just et al., FSE'14) — correlation, not identity. Topping this board may not fully predict real-world bug-finding. The eventual answer is a small real-bug "wild" split to validate that seeded-rank ≈ real-rank.
  • Scoring is uncalibrated until we see model spread. Tier weights, the 0.25 penalty, budgets and the zero-defect fraction are reasoned starting points, not tuned ones. W = 0.035 is the exception — it is derived, pinned just under the corpus's smallest quality gap.
  • Discrimination is demonstrated across both shipped tiers, at small n. Full easy- and medium-tier boards now separate models (and separate the same model with and without device tools). Most apps still have one episode per condition; it is not yet evidence the benchmark ranks models in general.
  • Probes can't discriminate single-screen apps. Every opencalc area shows the same keypad and taps carry coordinates, not labels, so those areas lean on the work-before-claim rule.
  • Loops no longer evade counting. for i in $(seq 30); do adb ...; done used to charge one step for thirty operations; the meters now sit on the adb socket below the agent, so every operation is counted however it was issued.
  • n is small. Most apps have one episode per condition. Quote means with trials, or don't quote them.
  • Scope. This measures functional-bug detection — not usability, visual, performance, accessibility or journey testing. "Best functional-bug-finding mobile benchmark" is the honest claim.
